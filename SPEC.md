# Todo App — Specification

## 1. Overview

A full-stack todo app with user accounts. Each user signs up with email and password, logs in, and manages **their own** todos with full CRUD (**create**, **read**, **update**, **delete**). Todos are stored in Postgres and are only visible to the user who created them. The app is deployed on Vercel from GitHub.

This is also a learning project, so the stack favors seeing how things work (auth and data access live inside the app) over the fastest possible setup.

### Goals
- Email/password sign-up, log-in and log-out
- CRUD for todos, scoped per user
- Server-side data access with type safety from the database to the UI
- Automatic deploys from GitHub to Vercel

### Non-Goals (v1)
- Social / OAuth login, magic links, 2FA
- Email verification and password reset (these need an email provider; see 13)
- Sharing todos or collaboration
- Due dates, reminders, notifications
- Offline support

## 2. Tech Stack

| Concern         | Choice                                                              |
|-----------------|---------------------------------------------------------------------|
| Framework       | **Next.js 16** with the **App Router** (`app/`)                 |
| Language        | **TypeScript**, `strict: true`                                      |
| UI              | React 19 (Server Components by default, Client Components where needed) |
| Styling         | **Tailwind CSS v4**                                                 |
| Database        | **Postgres on Neon** (free tier)                                    |
| ORM             | **Prisma 7** (`prisma-client` generator, `@prisma/adapter-pg` driver adapter, `prisma.config.ts`) |
| Auth            | **Better Auth** (email/password, database sessions via the Prisma adapter) |
| Mutations       | **Server Actions**                                                  |
| Input validation| **Zod** (shared by forms and Server Actions)                         |
| Testing         | Vitest (unit + integration), Playwright (end-to-end, optional in v1) |
| Linting         | ESLint (flat config) + `tsc --noEmit`                               |
| Hosting         | **Vercel**, connected to GitHub                                     |
| Dev tool        | Claude Code in the project folder                                   |
| Runtime         | Node.js 20.9+                                                       |

### Why these choices
- **Neon over Supabase:** auth is handled by Better Auth inside the app, so we only need plain Postgres. Neon is plain Postgres, has a Vercel integration, and can create a database branch per preview deploy.
- **Prisma over Drizzle:** the schema file and query API (`prisma.todo.findMany({ where: ... })`) read much like Rails' ActiveRecord.
- **Better Auth over Auth.js / Supabase Auth:** Better Auth supports email/password with database sessions out of the box, stores users and sessions in our own Postgres through Prisma, and keeps the login flow visible in our code.

## 3. Data Model

### 3.1 Auth tables
Generated by the Better Auth CLI into `prisma/schema.prisma`: `User`, `Session`, `Account`, `Verification`. Don't hand-edit their core fields; regenerate when Better Auth config changes. Passwords are hashed by Better Auth and stored on `Account`, never on `User`.

### 3.2 Todo

```prisma
model Todo {
  id        String   @id @default(cuid())
  title     String   @db.VarChar(200)
  completed Boolean  @default(false)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt])
  @@map("todos")
}
```

Add `todos Todo[]` to the generated `User` model.

### 3.3 Validation (Zod, `lib/validation.ts`)

```ts
export const todoTitleSchema = z
  .string()
  .trim()
  .min(1, "Todo can't be empty.")
  .max(200, "Keep it under 200 characters.");
```

Sign-up: name 1–100 chars, valid email, password 8–128 chars. The same schemas are used on the client (for instant feedback) and in Server Actions (the real check — never trust client input).

## 4. Pages and Routes

| Route                       | Type                 | Access        | Purpose                              |
|-----------------------------|----------------------|---------------|--------------------------------------|
| `/`                         | Server Component     | Public        | Redirects to `/todos` if logged in, else `/login` |
| `/signup`                   | Page + Client form   | Logged out    | Create an account                    |
| `/login`                    | Page + Client form   | Logged out    | Log in                               |
| `/todos`                    | Server Component     | **Logged in** | The todo app                         |
| `/api/auth/[...all]`        | Route Handler        | —             | Better Auth endpoints (`toNextJsHandler(auth)`) |

- Logged-in users visiting `/login` or `/signup` are redirected to `/todos`.
- Logged-out users visiting `/todos` are redirected to `/login`.
- `proxy.ts` (Next.js 16's replacement for `middleware.ts`) may do a fast **cookie-presence** redirect for UX, but it is **not** the security check. Every page and Server Action that touches user data checks the session on the server itself.
- `proxy.ts` only redirects **cookie-less** visitors away from `/todos`. It must not redirect cookie holders away from `/login` / `/signup`: a stale cookie would loop `/login` ↔ `/todos`. Those pages do a real session check (inside `<Suspense>`) instead.

## 5. Functional Requirements

### 5.1 Authentication
- **Sign up:** name, email, password. On success the user is logged in and sent to `/todos`. Duplicate email shows *"An account with this email already exists."*
- **Log in:** email, password. Wrong credentials show one generic message: *"Email or password is incorrect."* (don't reveal which one was wrong).
- **Log out:** button in the header on `/todos`; ends the session and redirects to `/login`.
- All three are real `<form>`s posting to Server Actions in `app/(auth)/actions.ts`, so they work without JavaScript. With JS they show a pending state, and a failed sign-up / log-in keeps the name and email (never the password).
- Sessions are stored in the database and last 7 days (Better Auth default), refreshed on activity.
- Better Auth's built-in rate limiting is on for sign-in and sign-up.

### 5.2 Create
- A text input with an **Add** button at the top of `/todos`.
- **Enter** or **Add** submits a `<form>` bound to the `createTodo` Server Action.
- The new todo appears at the **top** of the list. The input clears and keeps focus.
- Invalid input shows an inline error and creates nothing.
- The form works without JavaScript (progressive enhancement); with JS it shows a pending state on the button.

### 5.3 Read
- `/todos` lists **only the current user's** todos, newest first, fetched in the Server Component.
- Each item shows a checkbox, the title, and Edit / Delete controls.
- Completed todos are visually distinct (strikethrough, muted).
- Empty state: *"No todos yet — add one above."*
- Footer: *"N items left"* (singular "item" for 1).
- `app/todos/loading.tsx` shows a skeleton while data loads.

### 5.4 Update
- **Toggle complete:** clicking the checkbox calls `toggleTodo`. The UI updates instantly with `useOptimistic` and rolls back if the action fails.
- **Edit title:**
  - **Edit** (or double-click the title) switches to an input pre-filled with the title.
  - **Enter** / **Save** calls `updateTodo`; **Escape** / **Cancel** discards.
  - An empty title is rejected with an inline error (it does **not** delete the todo).
  - Only one todo is in edit mode at a time.

### 5.5 Delete
- **Delete** on an item calls `deleteTodo` and removes it (optimistically).
- **Clear completed** in the footer calls `clearCompleted`. It's disabled when nothing is completed.

### 5.6 Filtering (nice to have)
- Tabs: **All** | **Active** | **Completed**, stored in the URL as `?filter=active` so it survives reloads and can be shared.
- Filtering happens in the database query, read from `searchParams` in the page.

## 6. Server Actions

All in `app/todos/actions.ts` (`"use server"`).

| Action            | Input                     | Effect                                                         |
|-------------------|---------------------------|----------------------------------------------------------------|
| `createTodo`      | `title`                   | Insert todo for current user                                   |
| `toggleTodo`      | `id`                      | Flip `completed` on the user's todo                            |
| `updateTodo`      | `id`, `title`             | Change title on the user's todo                                |
| `deleteTodo`      | `id`                      | Delete the user's todo                                         |
| `clearCompleted`  | —                         | Delete all of the user's completed todos                       |

Every action follows the same steps:
1. **Authenticate:** `const user = await requireUser()` (from `lib/session.ts`; reads the session with `auth.api.getSession({ headers: await headers() })`). Throws / redirects if not logged in.
2. **Validate** input with Zod. Return `{ ok: false, error }` on failure.
3. **Authorize** by scoping every query to the user: `where: { id, userId: user.id }`. Use `updateMany` / `deleteMany` with that filter and treat `count === 0` as "not found". A user can never read or change another user's todo, even by guessing an id.
4. **Write** with Prisma.
5. **Revalidate:** `revalidatePath("/todos")`.
6. **Return** `{ ok: true }` or `{ ok: false, error: string }` (type `ActionResult`). Never return raw database errors to the client; log them on the server.

### Server vs Client Components
- Pages, layouts and data fetching are **Server Components**.
- Client Components only where there's interactivity: forms with pending state, optimistic toggles, edit mode, auth forms.
- `lib/prisma.ts`, `lib/auth.ts` and `lib/session.ts` start with `import "server-only"` so they can't be pulled into client code.

## 8. Configuration

### 8.1 Environment variables (`.env.example`)

```bash
# Neon — pooled connection string, used by the app at runtime
DATABASE_URL="postgresql://...-pooler.../neondb?sslmode=require"
# Neon — direct (unpooled) connection string, used by Prisma CLI for migrations
DIRECT_URL="postgresql://.../neondb?sslmode=require"

# Better Auth
BETTER_AUTH_SECRET="generate-with: openssl rand -base64 32"
BETTER_AUTH_URL="http://localhost:3000"
```

### 8.2 Prisma 7
- `schema.prisma` generator: `provider = "prisma-client"`, `output = "../generated/prisma"`. The datasource block has `provider = "postgresql"` and **no `url`**.
- `prisma.config.ts` at the project root: `import "dotenv/config"`, schema path, migrations path, and `datasource.url = process.env.DIRECT_URL`. (Prisma's `env()` helper throws when the variable is unset, which would break `prisma generate` in `postinstall` on a fresh clone or CI; `migrate` still errors clearly if the URL is missing.)
- `lib/prisma.ts`: `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })`, cached on `globalThis` in development to avoid exhausting connections during hot reload.
- Import the client from `@/generated/prisma/client`.

### 8.3 Better Auth
- `lib/auth.ts`: `betterAuth({ database: prismaAdapter(prisma, { provider: "postgresql" }), emailAndPassword: { enabled: true, minPasswordLength: 8, maxPasswordLength: 128 }, plugins: [nextCookies()] })` — `nextCookies()` must be the last plugin so Server Actions can set the session cookie.
- Auth goes through **Server Actions** (`app/(auth)/actions.ts`) calling `auth.api.signUpEmail` / `signInEmail` / `signOut` with `headers: await headers()`. There is no browser auth client. Better Auth error codes (`USER_ALREADY_EXISTS*`, `INVALID_EMAIL_OR_PASSWORD`) map to the messages in §5.1; anything else gets a generic message and is logged on the server.
- `lib/session.ts`: `getUser()` (wrapped in React `cache()`, so one lookup per request) and `requireUser()`. They read `headers()`, so with `cacheComponents` every component that calls them renders inside `<Suspense>`.
- Generate the auth tables with the Better Auth CLI, which is now the `auth` npm package (`@better-auth/cli` is deprecated): `npx auth generate --adapter prisma --dialect postgresql --output prisma/schema.prisma`. The CLI refuses to load a config that imports `server-only`, so run it against a temporary copy of the `lib/auth.ts` options without the database import. Then create a Prisma migration.

## 9. UI / UX

### Layout
- **Auth pages:** centered card with the form, a link to the other auth page.
- **`/todos`:** header (app name, user's name, Log out) → create form → filter tabs → list → footer.
- Centered column `mx-auto max-w-xl px-4`, responsive down to 320px.

### Styling (Tailwind)
- Utility classes only; `globals.css` holds the Tailwind import and minimal base styles.
- Completed: `line-through text-gray-400`. Errors: `text-sm text-red-600`.
- Edit / Delete visible on hover and focus, always visible on touch screens.
- Dark mode via the `dark:` variant (follows system setting).
- Buttons show a disabled/pending state while an action is running.

### Accessibility
- All inputs have `<label>`s (`sr-only` is fine); password fields use `autocomplete="current-password"` / `"new-password"`.
- Native checkboxes with `aria-label` like *"Mark 'Buy groceries' as complete"*.
- Full keyboard support; visible `focus-visible` styles.
- Errors use `role="alert"` and `aria-describedby`.
- Filter tabs use `aria-current` for the active tab.
- WCAG 2.1 AA contrast in light and dark mode.

## 10. Security

- Every Server Action and protected page checks the session **on the server**. `proxy.ts` is only a convenience redirect.
- Every todo query is scoped by `userId`. No endpoint accepts a `userId` from the client.
- All input is validated with Zod on the server.
- Secrets live only in environment variables; `.env` is gitignored. Nothing secret uses the `NEXT_PUBLIC_` prefix.
- Session cookies are `httpOnly`, `secure` in production, `sameSite=lax` (Better Auth defaults).
- Server Actions get Next.js's built-in origin check against CSRF.
- Errors shown to users are generic; details go to server logs only.

## 11. Testing

### Unit (Vitest)
- Zod schemas: empty, whitespace-only, 200 chars (valid), 201 chars (invalid), trimming.
- Pure helpers (e.g. "items left" pluralization, filter → Prisma `where` mapping).

### Integration (Vitest, against a separate test database)
- Use a dedicated Neon branch (or local Postgres) via `DATABASE_URL` in `.env.test`; reset tables between tests. **Never run tests against production.**
- Mock `requireUser()` to return a test user.
- Each Server Action: happy path, invalid input, and **user A cannot toggle / update / delete user B's todo**.

### End-to-end (Playwright, optional in v1)
- Sign up → add todo → toggle → edit → delete → log out → log back in and see todos persisted.
- Logged-out visit to `/todos` redirects to `/login`.

## 12. Setup, Scripts and Deployment

### Local setup

```bash
npx create-next-app@latest todo-app --typescript --tailwind --eslint --app --no-src-dir --import-alias "@/*"
cd todo-app
npm install @prisma/client @prisma/adapter-pg better-auth zod server-only
npm install -D prisma dotenv vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom
npx prisma init                      # then edit schema + prisma.config.ts per §8.2
npx auth generate --adapter prisma --dialect postgresql --output prisma/schema.prisma  # adds auth models (see §8.3)
npx prisma migrate dev --name init
npm run dev
```

### `package.json` scripts

```json
{
  "dev": "next dev",
  "build": "prisma generate && next build",
  "start": "next start",
  "lint": "eslint .",
  "typecheck": "tsc --noEmit",
  "test": "vitest run",
  "test:unit": "vitest run --project unit",
  "test:watch": "vitest",
  "test:db:deploy": "DOTENV_CONFIG_PATH=.env.test prisma migrate deploy",
  "test:e2e": "playwright test",
  "db:migrate": "prisma migrate dev",
  "db:deploy": "prisma migrate deploy",
  "db:studio": "prisma studio",
  "postinstall": "prisma generate"
}
```

Note: Next.js 16 removed `next lint`; ESLint runs directly.

### Deployment (Vercel + GitHub)
1. Push the repo to GitHub; import it in Vercel.
2. Add the **Neon integration** in Vercel. It sets `DATABASE_URL` / `DIRECT_URL` and can create a **database branch per preview deployment**, so previews never touch production data.
3. Set `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` (the deployed URL) per environment.
4. Every push to `main` deploys to production; every PR gets a preview URL.
5. Migrations: run `prisma migrate deploy` against production before or during deploy (e.g. a Vercel build step `npm run db:deploy && npm run build` for production only). Migrations are created locally with `prisma migrate dev` and committed.

## 13. Acceptance Criteria

The app is complete when:
- [ ] A user can sign up, log in and log out with email and password
- [ ] Logged-out users can't reach `/todos`; logged-in users skip `/login` and `/signup`
- [ ] A user can create a todo; invalid input is rejected with a message
- [ ] A user sees only their own todos, newest first, with loading and empty states
- [ ] A user can toggle, edit (save / cancel) and delete a todo, and clear completed todos
- [ ] Todos persist across reloads, log-outs and devices
- [ ] Integration tests prove one user can't read or change another user's todos
- [ ] The app works with keyboard only
- [ ] `npm run typecheck`, `npm run lint` and `npm test` pass
- [ ] The app is deployed on Vercel from GitHub, with preview deploys on PRs
